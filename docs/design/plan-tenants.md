# テナント分離（案A: 本格的なテナント分離）

デモ用の公開アカウントと、実際に家族が使うデータを**同じDBの中で確実に分ける**ための設計。
「デモ管理者が家族の書類を見られてしまう」「グループ名が全体で一意で他人の存在が推測できる」
といった問題を、データ分離の境界＝**テナント**を導入して解消する。

## 1. 何を分けるか

| 単位 | 説明 |
|---|---|
| **テナント (tenant)** | 利用する世帯/組織。データ分離の最上位の境界 |
| グループ | テナント内の共有単位（家族・部署）。**テナントをまたがない** |
| ドキュメント単位ACL | 同一テナント内のユーザーにだけ付与できる |

`users` / `groups` / `documents` / `notifications` は必ず1つのテナントに属する。
一覧・検索・通知のクエリは**すべてテナント条件で絞り込む**。

## 2. ロール

| ロール | 範囲 | できること |
|---|---|---|
| `super_admin`（全体管理者） | 全テナント | テナントの作成/変更/削除、ユーザーのテナント移動、全テナントのデータ閲覧 |
| `admin`（管理者） | 自テナント内 | 自テナントのユーザー・グループ管理、テナント内の全ドキュメント閲覧、ログ照会 |
| `registrar`（登録者） | 自テナント内 | 撮影・登録、自分/共有された書類の閲覧 |
| `viewer`（閲覧者） | 自テナント内 | 共有された書類の閲覧 |

- `super_admin` は**テナントに所属しない**（`users.tenant_id` が NULL なのはこのロールだけ）。
- 従来の「管理者は全件見える」は「**テナント管理者は自テナントの全件が見える**」に変わる。

## 3. リクエストのテナント解決

`app/api/deps.py` の `tenant_scope` が1リクエストで扱うテナントを決める。

| ログイン中のロール | `X-Tenant-Id` ヘッダ | スコープ |
|---|---|---|
| super_admin 以外 | 無視 | 自分の `tenant_id`（固定） |
| super_admin | 未指定 | `None` = 全テナント横断 |
| super_admin | 指定 | そのテナント |

クエリには `tenant_clause(Model.tenant_id, scope)` を付ける（`scope=None` なら無条件）。
作成系（ドキュメント/グループ）はテナントが定まらないと実行できないため `require_tenant` を使う。

## 4. アクセス判定（`can_access`）

```
super_admin                              → 常に可
別テナントの書類                          → 常に不可（所有者/ACL/ロールに関わらず）
同一テナント & (テナント管理者 or 所有者)  → 可
同一テナント & per-user ACL が必要権限以上 → 可
同一テナント & 閲覧 & 所有者と同じグループ → 可（グループ自動共有 F-36）
```

存在自体を伏せるため、別テナントのリソースは 403 ではなく **404** を返す。

## 5. 検索

OpenSearch の索引に `tenant_id`（keyword）を追加し、検索時に必ず term フィルタを掛ける。
索引が古い場合に備え、返す直前に DB 側でも `tenant_id` 一致と `can_access` を再確認する（二重の防御）。

| ロール | 索引フィルタ |
|---|---|
| super_admin（横断時） | なし |
| テナント管理者 | `tenant_id` のみ |
| 一般ユーザー | `tenant_id` + (所有者が自分/同一グループ ∪ 個別共有) |

テナント導入前に索引したドキュメントには `tenant_id` が無く、そのままでは検索に出てこない。
OCRワーカーの定期処理 `backfill_search_tenant` が索引を走査して DB のテナントを埋め直す。

## 6. 通知

`notifications.tenant_id` を追加し、書類のテナントを引き継ぐ。一覧・未読数・一括既読は
テナント条件付き。ユーザーが別テナントへ移っても、以前のテナントの通知は見えない。

## 7. スキーマ移行（Alembic 導入までの暫定措置）

`app/db/migrate.py` を起動時に実行する（冪等・PostgreSQL 限定）。

1. `ALTER TYPE role ADD VALUE IF NOT EXISTS 'super_admin'`
2. `users` / `groups` / `documents` / `notifications` へ `tenant_id UUID REFERENCES tenants(id)` を追加
3. バックフィル
   - ユーザー・グループ: `SEED_LEGACY_TENANT_SLUG` のテナント（既定 `family` = 実利用）
   - ドキュメント: 所有者のテナント
   - 通知: 書類 → 受信者の順に引き継ぐ
4. `documents.tenant_id` / `groups.tenant_id` を NOT NULL 化
5. グループ名の一意制約を「全体で一意」から「`(tenant_id, name)` で一意」へ張り替え

> 既存データは既定で**実利用テナント**に入る。デモ側へ寄せたい場合は初回起動前に
> `SEED_LEGACY_TENANT_SLUG=demo` を設定する。起動後でも「ユーザー管理」の
> テナント列（全体管理者のみ表示）から移動できる。

## 8. 初期投入

| アカウント | ロール | テナント | 公開 | 既定の認証情報 |
|---|---|---|---|---|
| `SEED_SUPER_ADMIN_EMAIL`（既定 空＝作成しない） | super_admin | なし | **非公開** | 指定時のみ作成。パスワード未設定なら**自動生成してログに1度だけ出力**。通常は既存ユーザーを DB で昇格させる |
| `SEED_ADMIN_EMAIL`（既定 `admin@example.com`） | admin | 実利用（`family`） | 非公開 | `admin123`（要変更） |
| `SEED_DEMO_ADMIN_EMAIL`（既定 `demo@example.com`） | admin | デモ | **公開** | `SEED_DEMO_PASSWORD`（既定 `demo123`） |
| `SEED_DEMO_REGISTRAR_EMAIL`（既定 `demo-registrar@example.com`） | registrar | デモ | **公開** | 同上 |
| `SEED_DEMO_VIEWER_EMAIL`（既定 `demo-viewer@example.com`） | viewer | デモ | **公開** | 同上 |

公開するのは**デモテナントの 管理者 / 登録者 / 閲覧者 の3つだけ**。ロールごとの見え方を
試せるよう、この3人はデモ用グループ（`SEED_DEMO_GROUP_NAME`、既定「デモ家族」）に所属させる
（グループ自動共有 F-36 で管理者が登録した書類を登録者・閲覧者も閲覧できる）。
ログイン画面（Web/モバイル）にこの3つをボタンで並べ、クリックで認証情報が入る。

**全体管理者は非公開**でログイン画面にも載せない。テナントの作成やユーザーのテナント移動など、
運用作業のときだけ使う。テナント管理者からは見えない（`tenant_id` が NULL のためテナント絞り込みで
一覧に出ない）。

## 9. ユーザーのテナント移動

全体管理者が `PATCH /api/v1/users/{id}` に `tenant_id` を指定すると、
`app/services/tenants.py` が次をまとめて行う。

- 本人の `tenant_id` 更新
- 本人が所有するドキュメントの `tenant_id` 更新（検索索引の `tenant_id` も更新）
- 本人宛の通知の `tenant_id` 更新
- 移動で不整合になるもの（移動先以外のグループ所属、本人が関わる個別共有ACL）を解除

## 10. API

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/api/v1/tenants` | テナント一覧（全体管理者は全件、他は自分のテナントのみ） |
| POST | `/api/v1/tenants` | テナント作成（全体管理者） |
| PATCH | `/api/v1/tenants/{id}` | 名称・説明・デモ種別の変更（全体管理者） |
| DELETE | `/api/v1/tenants/{id}` | 削除（全体管理者・**空のテナントのみ**） |
| PATCH | `/api/v1/users/{id}` | `tenant_id` 指定でテナント移動（全体管理者） |

共通ヘッダ: `X-Tenant-Id`（全体管理者のみ有効。操作対象テナントの切り替え）

## 11. 画面

- 左メニュー **「テナント管理」**（全体管理者のみ）: 一覧・作成・名称変更・削除・操作対象の切替
- サイドバー下部の**操作対象テナント**セレクタ（全体管理者のみ）
- 「ユーザー管理」に**テナント列**（全体管理者のみ）。セレクタで移動、作成時も所属を選べる
- ユーザーチップに所属テナント名を表示

## 12. 動作確認済みの項目

実PostgreSQLで移行〜分離を検証（テナント導入前のスキーマを再現して `init_db` を実行）。

- 既存のユーザー/グループ/ドキュメント/通知が実利用テナントへ移行される
- `role` enum への `super_admin` 追加、NOT NULL 化、グループ名のテナント内一意への張り替え
- `init_db` の再実行（冪等性）
- デモ管理者から実利用テナントの書類が `can_access` で拒否される
- 一覧クエリがテナント外の書類を返さない
- ユーザーのテナント移動で所有ドキュメントも移り、テナント外のグループ所属が解除される

API（FastAPI TestClient）でも、デモ管理者 / 実利用の管理者 / 全体管理者の3者で次を確認した。

- ドキュメント一覧・取得・プレビュー・家族状況・コメントで別テナントは 404
- ユーザー一覧/更新/PWリセットが自テナントに限られる。テナント管理者は全体管理者を作れない
- グループはテナント内のみ。別テナントのユーザーはメンバーに追加できない。同名グループは併存できる
- 通知・未読数・ログがテナント内に限られる
- 検索索引が古くて別テナントの書類を返しても、API の応答からは除かれる
- 全体管理者は全テナントを横断でき、`X-Tenant-Id` で対象を絞れる
