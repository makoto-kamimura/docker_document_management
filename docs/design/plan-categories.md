## Context

- 全体管理者（`super_admin`）はテナント未所属で、`X-Tenant-Id` ヘッダを付けなければ**全テナントを横断**して見え、`can_access` も無条件に通していた。操作対象の切り替えは Web のサイドバー下部とモバイルの撮影画面（登録先の選択）の2か所にあった。
- 要望: テナントの機能は全体管理者だけが **Web の「テナント管理」からだけ**設定・確認・変更する。それ以外の機能は、全体管理者も他のユーザーと同じく**1つのテナントの中で**動く。
- カテゴリは自由入力の文字列（`documents.category`）で、見られる人には関係しなかった。要望: カテゴリそのものを追加でき、書類（画像）をカテゴリに入れて保管でき、**カテゴリごとに見られる人を決める**。サンプルは「投函チラシ＝全員」「重要書類＝子供以外」「処方箋＝本人だけ」。
- 確認済みの方針: 子供はユーザーに付ける「子供」の印で表す（ロールとは別）／公開範囲は**管理者・全体管理者にも適用**する（処方箋は本人以外は誰も見られない）／「画像の登録」は書類をカテゴリに入れること（カテゴリのアイコン画像は作らない）／カテゴリの管理はテナントの管理者が行う。

## A. 全体管理者は「操作中のテナント」1つの中で動く

- `users.active_tenant_id`（全体管理者だけが使う操作中のテナント）を追加する。`tenant_id` は NULL のままにし、テナント管理者のユーザー一覧には出さない。`User.scope_tenant_id` が一般ユーザーは `tenant_id`、全体管理者は `active_tenant_id` を返す。
- `deps.tenant_scope` は `X-Tenant-Id` を読まず、常に `scope_tenant_id` を返す（全体管理者が未選択なら 409）。scope が NULL にならないので `require_tenant`・`tenant_clause`・`in_scope`・`ensure_in_scope` は削除する。
- `can_access` の「全体管理者なら常に可」をやめ、操作中のテナントの中でテナント管理者と同じに扱う。
- テナント API はすべて全体管理者だけ。追加: `PUT /tenants/active`（切り替え）、`GET /tenants/{id}/users`（メンバー）、`PUT /tenants/{id}/users/{user_id}`（テナント間の移動。`PATCH /users/{id}` の `tenant_id` はなくす）。`POST /tenants` でサンプルのカテゴリも作り、`DELETE` ではカテゴリを消して、そのテナントを操作中にしていた全体管理者を未選択に戻す。
- 起動時、操作中のテナントが未選択の全体管理者には実利用テナントを割り当てる。
- Web: サイドバーの切り替えを削除し、テナント管理の「このテナントを操作」で切り替える。メンバーの確認と移動もテナント管理へ移す（ユーザー管理のテナント列は削除）。未選択なら各画面の上に案内を出す。
- モバイル: 登録先テナントの選択と `X-Tenant-Id` を削除し、未選択なら案内を出す。

## B. 子供の印

- `users.is_child`。Web のユーザー管理で切り替える。デモに `demo-child@example.com`（登録者・子供）を追加する。

## C. カテゴリ（マスタ＋公開範囲）

- `categories`（`tenant_id`, `name`, `visibility`, `sort_order`。名前はテナント内で一意）と `documents.category_id`。未分類（NULL）は「家族」と同じに扱う。
- 公開範囲は見られる人の上限で、管理者・全体管理者・個別共有にも当てはめる。

| 公開範囲 | 閲覧できる人 |
|---|---|
| 全員（`everyone`） | テナントの全員 |
| 子供以外（`adults`） | 子供の印がない全員＋登録者本人 |
| 家族（`family`）・未分類 | 今と同じ（登録者・同じグループ・個別共有・管理者） |
| 本人だけ（`owner`） | 登録者だけ |

- 判定順: テナント → 登録者 → 公開範囲 → 管理者 → 個別共有 → グループ / 全員 / 子供以外。`deps.can_access` に実装し、同じ条件を SQL にした `deps.visible_documents_clause` を一覧・検索・ログ・通知・カテゴリの件数で使う。見られない書類は 404（見られるが権限が足りなければ 403）。
- `services/family.family_ids_map`（通知・リマインド・確認人数の相手）も公開範囲に合わせる。
- 検索: 閲覧できる書類の ID を DB で求めて `ids` フィルタで渡す。カテゴリは名前・範囲が変わるため索引に持たせず、ヒットのカテゴリ名は DB から付ける。パラメータは `category` → `category_id`。
- カテゴリの API: `GET /categories`（誰でも。件数は自分が見られる書類だけ）、`POST` / `PATCH` / `DELETE`（管理者。書類が1件でもあれば削除できない。見えない書類も数え、範囲を勝手に広げない）。`POST /documents` と `PATCH /documents/{id}` は `category_id` を受け、同じテナントのカテゴリでなければ 400。
- 文書解析が推定する分類（学校・行政など）は、空のカテゴリではなく空の書類種別に入れる（自動で見られる人を変えない）。
- 移行: 旧 `documents.category` の文字列は書類種別へ（書類種別があればタグへ）移して列を削除し、書類は未分類にする（今見えている範囲を変えない）。カテゴリ導入前の DB では、今あるテナントすべてにサンプルのカテゴリを作る。
- Web: 「カテゴリ管理」画面（管理者）、一覧のカテゴリでの絞り込み、編集画面のカテゴリ選択、本人だけの鍵の印、権限設定画面の注記。
- モバイル: 撮影の確認画面でカテゴリを選び、選んだ範囲を一行で出す。送信待ちにもカテゴリを持たせる。一覧の絞り込みと、一覧・詳細のカテゴリ表示。

## 確認した結果

- バックエンドの単体テスト `tests/test_category_visibility.py`（SQLite）: 範囲ごとに、登録者・大人・子供・管理者・グループ外・別テナント・全体管理者（操作中／別テナント／未選択）について、`can_access` と `visible_documents_clause` が一致し期待どおりになること、個別共有で範囲を広げられないこと、`family_ids_map`、テナント API の権限・切り替え・`X-Tenant-Id` の無視・メンバーの移動、カテゴリ API（権限・重複・削除の制限・件数）、別テナントのカテゴリを付けられないこと。既存のテストと合わせて 38 件が通る。
- 実 PostgreSQL での移行: 旧版のコードで作ったスキーマに、旧カテゴリつきの書類を入れて `init_db` を2回実行した。旧カテゴリが書類種別・タグへ移り、列が消え、両テナントにサンプルのカテゴリができ、全体管理者が実利用テナントを操作中になり、2回目は何も変えないこと。
- 実環境（PostgreSQL・OpenSearch・MinIO・バックエンド・OCR ワーカー）での通し確認: デモの登録者がチラシ・重要書類・処方箋・未分類を撮影して OCR が終わったあと、一覧・詳細・検索・通知が、管理者・閲覧者・子供・全体管理者でそれぞれ表のとおりになること。範囲を狭めると一覧と通知から消えること、子供の印を外すと重要書類が見えること、全体管理者が切り替えたテナントの分だけを扱うこと。
- Web・モバイルは型チェック（`tsc`）と Web のビルドまで。実機の Expo Go での確認は未実施（T-1308）。
